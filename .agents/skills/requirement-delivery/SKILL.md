# Requirement Delivery

将 RealmFlow 的单个需求从产品文档推进到可验收实现。整个流程必须保持需求、代码、测试和文档状态一致。

## 适用场景

以下情况必须使用本 Skill：

- 用户要求实现某个产品需求或功能。
- 用户要求修复缺陷、调整行为或进行影响行为的重构。
- 用户要求从需求文档开始完成设计、开发和测试。
- 用户要求继续一个尚未完成的需求交付流程。

以下情况不使用：

- 纯解释、纯调研或代码阅读。
- 不影响产品行为的简单文案修改。
- 用户明确要求只做某个阶段时，不擅自越过该阶段。

## 强制原则

1. **需求是基线**：先定位对应的 `docs/product-requirements/**` 文档及上位架构文档。
2. **设计先行、默认自动执行**：修改生产代码前必须给出推荐实施设计和验收矩阵；除必须确认的例外场景外，不等待用户确认，直接按推荐方案进入计划与 TDD。
3. **严格 TDD**：先写测试、观察正确的失败，再写最小实现使其通过。
4. **Main 所有业务状态**：Electron Main 负责业务状态、文件系统副作用、事务和恢复；Renderer 只负责展示及发起类型化请求。
5. **本地优先**：业务数据和文件留在本地；除模型调用外不得引入隐式联网依赖。
6. **事务一致性**：状态迁移、持久化记录、文件操作及审计必须定义提交、回滚和幂等行为。
7. **开发期保持干净模型**：除非用户明确要求，不为未发布历史数据增加兼容分支；需要重置数据时先确认删除范围。
8. **保护工作区**：不得覆盖或回滚用户已有改动；不得提交 Git，除非用户明确要求。
9. **完成必须可证明**：只有测试、类型检查、构建和必要的实际界面验证完成后，才能标记已验收。

## 交付状态

需求文档使用以下状态：

```text
待细化 -> 已评审 -> 已规划 -> 实现中（RED） -> 实现中（GREEN） -> 已验收
```

用户只要求中间阶段时，停在对应状态，不提前标记完成。

## 阶段 1：读取上下文

1. 读取用户指定的需求文档。
2. 读取其引用的产品架构、领域规则和直接依赖。
3. 检查当前分支、工作区状态及相关实现和测试。
4. 识别已有能力、缺口、数据所有权、事务边界和兼容约束。
5. 对缺陷先复现或获得直接证据，不凭表象修改代码。

输出应明确：

- 当前行为。
- 目标行为。
- 已确认根因或尚待验证的假设。
- 本次范围与非目标。

## 阶段 2：补全需求

需求文档至少补齐：

- 目标、范围、非目标。
- 用户故事。
- 功能规则与不变量。
- 正常、取消、失败、冲突、并发和恢复行为。
- 数据所有权及 Renderer、Main、Sidecar 边界。
- 持久化、事务、回滚和幂等规则。
- 用户可见错误。
- 可自动化的测试矩阵。

验收标准必须使用 Given/When/Then 或同等明确的可验证描述。

## 阶段 3：设计决策

提供 1 个推荐方案；存在实质取舍时再提供 1 至 2 个备选方案。

设计必须覆盖：

- 受影响的模块和契约。
- 数据流与状态变化。
- 文件系统及数据库一致性。
- 错误处理和恢复。
- 测试层级与验收方式。

完成设计后默认视为用户授权执行推荐方案，不单独发起确认，不因等待反馈而中断交付。用户已指定方案时直接采用该方案。

只有以下情况必须暂停并请求用户确认：

- 数据删除、覆盖用户文件、强制推送或其他不可逆操作。
- 发送消息、发起审批、产生费用、发布上线等显著外部副作用。
- 多种解释会导致明显不同的产品行为，且无法从需求、代码或既有约定中确定安全默认值。
- 用户明确要求先审阅方案、规格或计划再实施。

除上述情况外，Agent 应自行做出保守、可验证且符合现有架构的决策，并在最终报告中说明采用的方案。

## 阶段 4：制定实施计划

计划按可验证增量拆分：

1. 基线验证。
2. RED 测试。
3. 最小 GREEN 实现。
4. 重构与架构守卫。
5. 聚焦测试。
6. 全量验证。
7. 实际界面或运行时验收。
8. 文档状态回写。

每次只允许一个步骤处于进行中。

## 阶段 5：RED

1. 先运行相关既有测试，确认基线为绿。
2. 每个测试只表达一个用户可观察行为。
3. 优先测试真实应用服务、仓储和组件；仅在系统边界使用 mock。
4. 运行新增测试并确认失败原因：
   - 是断言失败，不是语法或环境错误。
   - 失败来自缺失行为，不是错误夹具。
   - 原有测试仍通过。
5. 记录 RED 结果后再进入实现。

缺陷测试必须能稳定复现原问题。

## 阶段 6：GREEN

1. 只实现使当前失败测试通过的最小行为。
2. 遵循仓库现有分层、端口和适配器模式。
3. 不顺手重构无关模块。
4. 文件操作与数据库写入必须保持既定事务边界。
5. 对 revision、状态门禁和重复请求保持确定行为。
6. 每完成一个增量立即运行对应测试。

## 阶段 7：重构与自审

测试转绿后才允许重构。自审重点：

- 是否破坏 Main 所有权或引入 Renderer 业务状态。
- 是否绕过 revision、审批、产物或工作流门禁。
- 是否留下部分文件或部分数据库状态。
- 是否错误增加历史兼容、隐式迁移或双写。
- 是否出现无测试的新分支。
- 是否影响用户已有改动。

## 阶段 8：验证

至少执行：

```bash
npm test -- <focused-test-files>
npm test
npm run typecheck
npm run build
git diff --check
```

根据改动补充：

- 数据库 schema、迁移和重启恢复验证。
- Electron Main/Preload channel 契约验证。
- 前端实际启动、关键交互和桌面/窄窗口截图。
- 文件系统结果及回滚结果检查。
- 架构测试和安全边界测试。

若全量测试包含存量 warning，说明其来源及是否由本次改动引入。

## 阶段 9：验收回写

完成后更新需求文档：

- 状态改为 `已验收`。
- 勾选已完成实现项。
- 记录实施日期、测试数量和验证命令。
- 记录保留风险或存量 warning。

最终报告只包含：

- 实现结果。
- 关键文件链接。
- 测试、类型检查、构建和实际验收结果。
- 未完成项或已知风险。
- Git 是否提交。

## 数据清理规则

数据删除是独立的破坏性操作：

1. 必须确认用户明确要求清理。
2. 先停止所有可能持有数据库或文件句柄的进程。
3. 区分应用数据目录、RealmFlow 管理目录和普通用户文件。
4. 只删除已确认属于 RealmFlow 的数据。
5. 清理后启动应用，验证空数据库、空业务列表和目标 schema。
6. 不以“兼容历史数据”为理由保留未发布阶段的废弃模型。

## 禁止事项

- 未形成推荐设计和验收矩阵就写生产代码。
- 在不存在必须确认的例外场景时，以等待方案确认为由中断交付。
- 未观察 RED 就声称使用了 TDD。
- 只运行聚焦测试便宣称需求完成。
- 为了让测试通过而削弱业务不变量。
- 未获授权清空数据、提交代码或推送远端。
- 将临时命令输出、凭据、用户路径或一次性数据写入 Skill。
