# Requirement Delivery

将 RealmFlow 的单个需求推进到可验收实现。先按风险和影响面选择
Lite 或 Full 模式，再让设计、测试和验收强度与改动规模匹配。

## 适用场景

以下情况必须使用本 Skill：

- 用户要求实现某个产品需求或功能。
- 用户要求修复缺陷、调整行为或进行影响行为的重构。
- 用户要求从需求文档开始完成设计、开发和测试。
- 用户要求继续一个尚未完成的需求交付流程。

以下情况不使用：

- 纯解释、纯调研或代码阅读。
- 不影响产品行为的简单文案修改。
- 用户明确要求只做某个阶段时，不擅自越过该阶段。

## 交付模式

开始工作时先判定模式，不为 Lite 需求创建规格、计划或额外确认环节。
无法确认影响面时使用 Full；执行中发现影响面扩大时立即升级为 Full。

### Lite：快速交付

只有同时满足以下条件时使用：

- 改动局限在一个清晰的前端组件、样式区域、文案或局部纯函数。
- 不改变 Main、Preload、IPC、Sidecar、数据库、文件系统或网络契约。
- 不涉及权限、安全、事务、并发、恢复、调度、工作流状态机或数据迁移。
- 不修改跨页面共享基础组件的公共 API，也不改变多个模块共同依赖的不变量。
- 失败影响局部、可立即回退，并可通过聚焦测试和目标 UI 状态充分证明。

典型 Lite：

- 单个选择器的间距、宽度、颜色、字号或响应式布局修复。
- 局部组件文案、图标和显隐条件调整。
- 单组件内、无持久化副作用的交互缺陷。

Lite 流程：

1. 读取目标实现、直接测试和真实 DOM/运行状态，确认根因。
2. 用一句话说明推荐改法，直接执行，不等待确认。
3. 先增加或更新聚焦回归测试并观察 RED；纯视觉缺陷可用稳定的样式断言或目标 UI 几何测量作为 RED 证据。
4. 实现最小修复，运行直接相关测试。
5. 只验收用户指定场景及相邻的一个关键状态，例如打开/关闭、宽/窄或启用/禁用。
6. 执行 `git diff --check`；按验证矩阵决定是否需要 typecheck 或 build。
7. 简洁报告结果，不创建规格文档、实施计划或验收报告，除非用户明确要求。

### Full：完整交付

满足任一条件时使用：

- 改变业务规则、领域模型、公共契约或跨模块数据流。
- 涉及 Main、Preload、IPC、Sidecar、数据库、文件系统、网络或外部副作用。
- 涉及权限、安全、事务、并发、恢复、调度、工作流状态机或数据迁移。
- 修改共享基础设施、架构边界或多个页面共同使用的组件行为。
- 大范围重构、缺陷根因不确定，或局部失败可能造成数据/执行状态不一致。
- 用户明确要求完整设计、全量回归或发布级验收。

Full 使用后续完整阶段，并执行全量验证。

## 强制原则

1. **风险决定流程**：先选 Lite 或 Full，不因流程模板扩大需求。
2. **设计强度匹配规模**：Lite 只需一句话改法和目标验收点；Full 才补全需求、设计和实施计划。
3. **默认自动执行**：除必须确认的例外场景外，不等待用户确认。用户已给出明确方案时直接实施。
4. **严格 TDD**：先写聚焦测试、观察正确的失败，再写最小实现使其通过；测试层级与风险匹配。
5. **Main 所有业务状态**：Electron Main 负责业务状态、文件系统副作用、事务和恢复；Renderer 只负责展示及发起类型化请求。
6. **本地优先**：业务数据和文件留在本地；除模型调用外不得引入隐式联网依赖。
7. **事务一致性**：状态迁移、持久化记录、文件操作及审计必须定义提交、回滚和幂等行为。
8. **开发期保持干净模型**：除非用户明确要求，不为未发布历史数据增加兼容分支；需要重置数据时先确认删除范围。
9. **保护工作区**：不得覆盖或回滚用户已有改动；不得提交 Git，除非用户明确要求。
10. **完成必须可证明**：Lite 用聚焦测试和针对性验收证明；Full 用聚焦测试、全量验证和运行时验收证明。
11. **禁止重复全量**：全量测试和生产构建只在最终代码稳定后执行一次。失败时先用聚焦命令定位修复，确认稳定后再补一次最终全量。
12. **开发期不生成发布产物**：开发阶段的功能和缺陷修复默认只做聚焦测试、必要 typecheck、目标运行时 smoke 与 `git diff --check`；不要生成 `RealmFlow.app`、`.pkg` 或 `.zip`。只有问题明确发生在打包产物，或改动直接触及 `electron-builder`、`app.asar`、`Contents/Resources`、native runtime 分发布局、安装器或签名链路时，才允许生成 `RealmFlow.app` 做产物级验证；`.pkg`、`.zip`、Developer ID 签名和 Apple 公证只属于发布/分发阶段。

## 交付状态（仅 Full 或已有需求文档）

需求文档使用以下状态：

```text
待细化 -> 已评审 -> 已规划 -> 实现中（RED） -> 实现中（GREEN） -> 已验收
```

用户只要求中间阶段时，停在对应状态，不提前标记完成。

## 阶段 1：读取上下文

1. 判定 Lite 或 Full，并记录触发依据。
2. Lite 只读取目标文件、直接测试和必要运行状态；Full 读取需求文档、上位架构和直接依赖。
3. 检查当前分支、工作区状态及相关实现和测试。
4. 对缺陷先复现或获得直接证据，不凭表象修改代码。

输出应明确：

- 当前行为。
- 目标行为。
- 已确认根因或尚待验证的假设。
- 本次模式；Lite 不需要展开非目标或形成独立文档。

## 阶段 2：补全需求（仅 Full）

需求文档至少补齐：

- 目标、范围、非目标。
- 用户故事。
- 功能规则与不变量。
- 正常、取消、失败、冲突、并发和恢复行为。
- 数据所有权及 Renderer、Main、Sidecar 边界。
- 持久化、事务、回滚和幂等规则。
- 用户可见错误。
- 可自动化的测试矩阵。

验收标准必须使用 Given/When/Then 或同等明确的可验证描述。

## 阶段 3：设计决策

Lite 给出一句话推荐改法和 1 至 3 个针对性验收点后直接执行，不列备选方案，
不请求设计确认，不创建规格文档。

Full 提供 1 个推荐方案；存在实质取舍时再提供 1 至 2 个备选方案。

Full 设计必须覆盖：

- 受影响的模块和契约。
- 数据流与状态变化。
- 文件系统及数据库一致性。
- 错误处理和恢复。
- 测试层级与验收方式。

完成设计后默认视为用户授权执行推荐方案，不单独发起确认，不因等待反馈而中断交付。用户已指定方案时直接采用该方案。

只有以下情况必须暂停并请求用户确认：

- 数据删除、覆盖用户文件、强制推送或其他不可逆操作。
- 发送消息、发起审批、产生费用、发布上线等显著外部副作用。
- 多种解释会导致明显不同的产品行为，且无法从需求、代码或既有约定中确定安全默认值。
- 用户明确要求先审阅方案、规格或计划再实施。

除上述情况外，Agent 应自行做出保守、可验证且符合现有架构的决策，并在最终报告中说明采用的方案。

## 阶段 4：制定实施计划（仅 Full）

计划按可验证增量拆分：

1. 基线验证。
2. RED 测试。
3. 最小 GREEN 实现。
4. 重构与架构守卫。
5. 聚焦测试。
6. 最终全量验证。
7. 实际界面或运行时验收。
8. 文档状态回写。

每次只允许一个步骤处于进行中。

## 阶段 5：RED

1. 运行最接近改动的既有测试，确认聚焦基线为绿；Lite 不为此运行全量测试。
2. 每个测试只表达一个用户可观察行为。
3. 优先测试真实应用服务、仓储和组件；仅在系统边界使用 mock。
4. 运行新增测试并确认失败原因：
   - 是断言失败，不是语法或环境错误。
   - 失败来自缺失行为，不是错误夹具。
   - 原有测试仍通过。
5. 记录 RED 结果后再进入实现。

缺陷测试必须能稳定复现原问题。

## 阶段 6：GREEN

1. 只实现使当前失败测试通过的最小行为。
2. 遵循仓库现有分层、端口和适配器模式。
3. 不顺手重构无关模块。
4. 文件操作与数据库写入必须保持既定事务边界。
5. 对 revision、状态门禁和重复请求保持确定行为。
6. 每完成一个增量立即运行对应测试。

## 阶段 7：重构与自审

测试转绿后才允许重构。自审重点：

- 是否破坏 Main 所有权或引入 Renderer 业务状态。
- 是否绕过 revision、审批、产物或工作流门禁。
- 是否留下部分文件或部分数据库状态。
- 是否错误增加历史兼容、隐式迁移或双写。
- 是否出现无测试的新分支。
- 是否影响用户已有改动。

## 阶段 8：验证

### Lite 验证矩阵

| 改动类型 | 必须验证 |
| --- | --- |
| CSS、布局、颜色、尺寸 | 相关样式/组件测试、目标 UI 状态、`git diff --check` |
| 局部文案或图标 | 相关组件/本地化测试、目标 UI 状态、`git diff --check` |
| 局部 React 交互 | 相关组件测试、`npm run typecheck`、目标 UI 交互、`git diff --check` |
| 局部纯函数 | 直接单元测试、受影响调用方测试、`npm run typecheck`、`git diff --check` |
| 文档或注释 | 内容检查、链接/格式检查、`git diff --check` |

Lite 默认不运行 `npm test` 全量测试，不运行生产构建。只有聚焦证据无法覆盖
改动、触及构建链路，或执行中升级为 Full 时才运行。

目标 UI 验收只覆盖需求场景和一个最相邻状态。优先复用已运行应用或热更新；
最多做一次最终重启，不为截图或测量反复重建应用。

开发阶段的 bug 修复默认不生成 `RealmFlow.app`、`.pkg` 或 `.zip`。只有以下情况才做
打包产物级验证：

- 用户明确要求验证打包应用、安装包或发布产物。
- 缺陷只在 packaged app 中复现，开发运行态无法证明修复。
- 改动直接影响 `electron-builder`、`app.asar`、`Contents/Resources`、DSH/native
  runtime 分发布局、安装器、签名或公证链路。

即使需要产物级验证，开发阶段也优先只验证 `RealmFlow.app`；不要生成 `.pkg` 或 `.zip`，
除非当前任务明确是发布/分发验收。

### Full 验证

最终代码稳定后执行一次：

```bash
npm test -- <focused-test-files>
npm test
npm run build
git diff --check
```

`npm run build` 已包含 typecheck 和架构守卫时，不再单独重复执行。

按风险补充：

- 数据库 schema、迁移和重启恢复验证。
- Electron Main/Preload channel 契约验证。
- 前端实际启动、关键交互和桌面/窄窗口截图。
- 文件系统结果及回滚结果检查。
- 架构测试和安全边界测试。

若测试包含存量 warning，只说明其是否由本次改动引入，不为无关 warning
扩大任务范围。

## 阶段 9：验收回写（仅 Full 或已有需求文档）

完成后更新需求文档：

- 状态改为 `已验收`。
- 勾选已完成实现项。
- 记录实施日期、测试数量和验证命令。
- 记录保留风险或存量 warning。

最终报告只包含：

- 实现结果。
- 关键文件链接。
- 测试、类型检查、构建和实际验收结果。
- 未完成项或已知风险。
- Git 是否提交。

## 数据清理规则

数据删除是独立的破坏性操作：

1. 必须确认用户明确要求清理。
2. 先停止所有可能持有数据库或文件句柄的进程。
3. 区分应用数据目录、RealmFlow 管理目录和普通用户文件。
4. 只删除已确认属于 RealmFlow 的数据。
5. 清理后启动应用，验证空数据库、空业务列表和目标 schema。
6. 不以“兼容历史数据”为理由保留未发布阶段的废弃模型。

## 禁止事项

- 对 Lite 需求创建规格、实施计划、长篇方案或额外确认门禁。
- 未判定交付模式就机械执行完整流程。
- 在不存在必须确认的例外场景时，以等待方案确认为由中断交付。
- 未观察 RED 就声称使用了 TDD。
- Lite 缺少目标 UI/运行状态证据便宣称完成。
- Full 只运行聚焦测试便宣称完成。
- 在代码尚未稳定时重复运行全量测试或生产构建。
- 为了让测试通过而削弱业务不变量。
- 未获授权清空数据、提交代码或推送远端。
- 将临时命令输出、凭据、用户路径或一次性数据写入 Skill。
